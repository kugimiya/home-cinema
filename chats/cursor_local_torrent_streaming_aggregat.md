# Проект: локальный стриминговый агрегатор торрентов с постоянным сидированием (аналог Zona для личного использования)

## 0. Контекст и цель

Я хочу построить приложение **исключительно для личного использования** (я и жена), которое позволяет искать фильмы и сериалы на русскоязычных торрент-трекерах, получать magnet-ссылку или .torrent-файл и **сразу смотреть видео через стриминг**, не дожидаясь полной загрузки.

**Ключевое требование:** пока я смотрю фильм или серию, файл должен **скачиваться на диск** (не только в оперативную память) и **оставаться там для раздачи** после окончания просмотра. Удаление файлов с диска и прекращение раздачи должно происходить **только вручную через админ-панель**. Я хочу быть активным сидером, а не только потребителем.

Я **не собираюсь** распространять само приложение как публичный сервис или предоставлять к нему доступ третьим лицам. Все компоненты работают локально на моей машине или в моей домашней сети. Это важный контекст: решения должны быть оптимизированы для локального, непубличного использования, но с полноценной раздачей.

Я буду писать код с твоей помощью (AI-агент), но **всю «обвязку» между готовыми инструментами** — логику поиска, оркестрацию, локальный HTTP-прокси для стриминга, интерфейс и админ-панель для управления файлами — мы делаем с нуля. Готовые инструменты используем как строительные блоки, а не пишем парсеры трекеров с нуля.

## 1. Саммари обсуждения и принятые решения

Мы уже обсудили несколько подходов и пришли к следующим выводам, которые нужно зафиксировать как **отправную точку**:

1. **Zona работает не как «облачный» сервис, а как локальный агрегатор.** Она поднимает локальный HTTP-сервер, встроенный BitTorrent-клиент скачивает файл последовательно, а видеоплеер читает поток с `localhost`. Библиотеки контента у Zona нет — она опрашивает публичные трекеры в реальном времени.
2. **Мы делаем не «одноразовый стриминг», а полноценный локальный медиа-сервер с сидированием.** Файлы после просмотра не удаляются автоматически. Они остаются на диске и раздаются до тех пор, пока я сам не удалю их через админку. Это принципиальное отличие от стандартного поведения TorrServer в режиме «только стриминг».
3. **Писать парсеры трекеров с нуля — плохая идея.** Cloudflare, капчи, кодировка Windows-1251, постоянные изменения вёрстки. Гораздо эффективнее использовать готовые агрегаторы и библиотеки, которые уже решили эти проблемы.
4. **Оптимальный путь для личного проекта:** развернуть локальный агрегатор (TorAPI или Prowlarr/Jackett), который даёт единый API для поиска по нескольким трекерам, и написать свою «обвязку» — от поиска до стриминга и управления файлами.
5. **Для стриминга и сидирования есть два пути:**
   - **Готовый TorrServer**: поддерживает дисковый кэш (`UseDisk = true`) и сохранение файлов после закрытия торрента (`RemoveCacheOnDrop = false`). Это самый быстрый способ получить работающую систему.
   - **Свой локальный прокси на базе `libtorrent`**: даёт полный контроль над `save_path`, `seed_mode` и управлением жизненным циклом торрента. Больше кода, но именно это ты хочешь сделать «с нуля» для оптимальной работы.
6. **Твоя задача — не написать всё с нуля, а написать оптимальную обвязку** между готовыми компонентами: агрегатором поиска, торрент-движком, локальным стримингом и админ-панелью управления файлами.

```
│  └─────────────┘     └──────────┬───────────┘                    │
│                                 │                                │

│                    │  │ Диск: save_path   │  │                   │
│                    │  │ (файлы остаются)  │  │                   │
│                    │  │ Режим: seed       │  │                   │
│                    │  └───────────────────┘  │                   │
│                    └────────────┬────────────┘                   │
│                                 │ pieces / stream                │

│                    │  (VLC / MPV / TV)       │                   │
│                    └─────────────────────────┘                   │
│                                                                  │
│  ┌──────────────────────────────────────────┐                    │
│  │  Админ-панель (твой код)                 │                    │
│  │  - Список скачанных файлов и торрентов   │                    │
│  │  - Статус раздачи (сиды, пиры, рейтинг)  │                    │
│  │  - Кнопка «Удалить» (файл + торрент)     │                    │
│  └──────────────────────────────────────────┘                    │
└──────────────────────────────────────────────────────────────────┘
```

**Поток данных:**
1. Пользователь вводит название фильма в UI.
2. Orchestrator отправляет запрос в Search Aggregator.
3. Агрегатор возвращает список раздач с magnet-ссылками, качествами, озвучками, сидами.
4. Пользователь выбирает раздачу; Orchestrator передаёт magnet-ссылку в Torrent Engine.
5. Torrent Engine начинает последовательную загрузку **сразу на диск** (не только в RAM) и отдаёт куски видео Local HTTP Proxy для немедленного воспроизведения.
6. После завершения загрузки файл **остаётся на диске** и торрент **переходит в режим сидирования**.
7. Плеер читает `http://localhost:PORT/stream/...` и воспроизводит видео.
8. В админ-панели я вижу все сохранённые торренты, могу управлять ими и удалять те, которые больше не нужны.

## 3. Рекомендуемый стек и инструменты

### 3.1. Слой поиска (Search Aggregator)

**Вариант A (рекомендуемый для простоты): TorAPI**

- **Что это:** Неофициальный REST API для RuTracker, Kinozal, RuTor и NoNameClub. Умеет искать по названию, возвращать magnet-ссылки, .torrent-файлы, подробную информацию о раздаче (качество, озвучка, размер, сиды/пиры), RSS-ленты.
- **Развёртывание:** Docker (`docker run -d --name TorAPI -p 8443:8443 lifailon/torapi:latest`) или npm.
- **API:** OpenAPI/Swagger спецификация, примеры в GitHub Wiki.
- **Плюсы:** Один API — четыре крупных русских трекера. Уже решены вопросы с кодировками и авторизацией.

**Вариант B (более мощный): Prowlarr + Jackett**

- **Что это:** Менеджер индексаторов, который агрегирует десятки трекеров и предоставляет единый API.
- **Развёртывание:** Docker.
- **Плюсы:** Огромная база трекеров, поддержка обхода Cloudflare через Byparr.

**Рекомендация:** Начни с **TorAPI**. Если каких-то трекеров не хватает — добавь Prowlarr как второй агрегатор.

### 3.2. Слой стриминга и сидирования (Torrent Engine)

**Вариант A (быстрый старт): TorrServer с дисковым кэшем**

- **Что это:** Готовый торрент-стриминг сервер, который **умеет сохранять данные на диск и продолжать раздачу**.
- **Ключевые настройки для нашего сценария (обязательно применить):**
  - **`UseDisk`** = `true` — включает дисковый кэш вместо RAM. По умолчанию `false` (только память).[reference:0]
  - **`TorrentsSavePath`** = путь к директории на диске, где будут храниться скачанные файлы (например, `/mnt/media/torrents`).[reference:1]
  - **`RemoveCacheOnDrop`** = **`false`** — **критически важно.** Если `true`, TorrServer удаляет дисковый кэш при закрытии/удалении торрента. Нам нужно `false`, чтобы файлы оставались на диске после просмотра и торрент мог продолжать раздачу.[reference:2][reference:3]
- **API:** REST API. Для управления торрентами можно использовать эндпоинты `/torrents` (добавление, список, удаление) и `/stream` (воспроизведение). Флаг `save_to_db` позволяет сохранять торрент в базу данных для управления.[reference:4][reference:5]
- **Как это работает для сидирования:** После завершения загрузки и просмотра файл остаётся в `TorrentsSavePath`. TorrServer продолжает раздавать его, пока торрент не будет удалён через API. `RemoveCacheOnDrop = false` гарантирует, что файлы не будут удалены автоматически.[reference:6]
- **Плюсы:** Не нужно писать свой прокси. Работает «из коробки». Поддерживает нужный нам сценарий с дисковым кэшем и сидированием.

**Вариант B (полный контроль, «с нуля»): `libtorrent` + свой HTTP-прокси + управление диском**

- **Что это:** Используем Python-биндинги `libtorrent` для управления торрент-сессией и пишем свой локальный HTTP-сервер, который отдаёт видеоплееру последовательный поток. Дополнительно реализуем логику **сохранения файлов на диск** и **продолжения раздачи** после завершения загрузки.
- **Ключевые функции libtorrent для нашего сценария:**
  - **`save_path`** — путь на диске, куда будут скачиваться файлы. Указывается в `add_torrent_params` при добавлении торрента.[reference:7]
  - **`set_sequential_download(True)`** — запрашивать куски по порядку для стриминга.
  - **`set_piece_deadline()`** — приоритизация кусков, которые нужны плееру «сейчас».
  - **`seed_mode`** — если файл уже полностью скачан, можно установить `seed_mode = True` в `add_torrent_params`, чтобы libtorrent сразу начал раздавать, не проверяя все куски заново (или проверяя их лениво).[reference:8]
  - **Сохранение состояния (resume data):** чтобы после перезапуска приложения торренты продолжали раздаваться с того же места, нужно сохранять `resume data` для каждого торрента и `session state` для сессии. Это позволяет восстанавливать прогресс и продолжать сидирование без повторной проверки файлов.[reference:9]
- **Управление жизненным циклом:** В админ-панели храним список активных торрентов с их `save_path`. Удаление торрента должно явно вызывать удаление файлов с диска (или перемещение в корзину) и остановку раздачи.
- **Плюсы:** Полный контроль над настройками, поведением загрузки, буферизацией и управлением файлами. Можно гибко настроить приоритеты и политику хранения.
- **Минусы:** Больше кода; нужно самостоятельно реализовать HTTP-прокси, обработку Range-запросов, буферизацию и персистентность состояния.
- **Референсы:** `XayOn/torrentstream`, документация libtorrent по `add_torrent_params`, `save_path`, `seed_mode`, `resume data`.

**Рекомендация:** Начни с **TorrServer** с настройками `UseDisk = true` и `RemoveCacheOnDrop = false` для быстрой проверки end-to-end сценария (поиск → стриминг → сохранение на диск → сидирование). Затем, если захочешь больше контроля, замени его на свой прокси на `libtorrent` с явным управлением `save_path` и `seed_mode`.

### 3.3. Обход Cloudflare и капч (если понадобится)

Если при прямом обращении к трекерам или при настройке Prowlarr/Jackett возникнут блокировки Cloudflare:

- **Byparr** — современная замена FlareSolverr на Camoufox (anti-detect Firefox), совместим с API FlareSolverr. Рекомендуется для новых челленджей.
- **FlareSolverr** — может не справляться с managed/Turnstile-челленджами.

**Практический вывод:** Если используешь Prowlarr/Jackett, настрой их на работу с **Byparr**.

### 3.4. Плеер

- **VLC** — универсальный, открывает HTTP-потоки, поддерживает большинство кодеков.
- **MPV** — лёгкий, хорошо работает с сетевыми потоками.
- **На TV:** клиент, который умеет открывать HTTP-URL, или web-интерфейс.

   - **Если используешь libtorrent:** проверить, что при добавлении торрента с `save_path` файлы сохраняются на диск, и после завершения загрузки торрент переходит в режим раздачи (`seed_mode` или просто `is_seeding()`).

### Задача 2: Реализация Orchestrator (обвязка)

**Цель:** Написать код, который связывает поиск, выбор раздачи, стриминг и управление файлами.

**Функциональность:**

- CLI или минимальный UI для ввода поискового запроса.
- Вызов API агрегатора (TorAPI или Prowlarr) и отображение результатов: название, качество, озвучка, размер, сиды.
- Выбор раздачи пользователем (или автоматический выбор по критериям).
- Передача magnet-ссылки в Torrent Engine (TorrServer API или libtorrent).
- Получение локального URL для стриминга и запуск плеера (VLC/MPV) или вывод URL для ручного открытия.
- **Управление сохранёнными файлами:** после завершения просмотра торрент остаётся в списке активных и продолжает раздаваться. Orchestrator должен предоставлять API для получения списка сохранённых торрентов, их статуса раздачи и удаления.

**Технические детали:**

- Язык: Python или Node.js (для libtorrent — Python).
- Конфигурация: пути к API агрегатора, `TorrentsSavePath` (директория для сохранения файлов), порт локального прокси — вынести в конфиг-файл или переменные окружения.
- Логирование: фиксировать запросы, ответы, magnet-ссылки, операции с файлами.

### Задача 3: Реализация локального стримингового прокси и управления диском (если выбран вариант с libtorrent)

**Цель:** Заменить TorrServer на собственный компонент для полного контроля над стримингом, сохранением на диск и сидированием.

**Функциональность:**

- Инициализация сессии `libtorrent` с настройками:
  - `set_sequential_download(True)`.
  - Управление `save_path` для каждого торрента (директория на диске).
- Добавление торрента по magnet-ссылке с `save_path`, указывающим на диск.
- Ожидание метаданных и определение файла видео.
- HTTP-сервер на `localhost`, который:
  - Поддерживает Range-запросы (для перемотки).
  - Отдаёт данные по мере поступления от libtorrent.
  - Использует `set_piece_deadline` для приоритизации кусков, которые нужны плееру «сейчас».
- **После завершения загрузки:** торрент **не останавливается**. Он продолжает раздаваться. Файлы остаются в `save_path`.
- **Персистентность:** сохранять `resume data` для каждого торрента и `session state` для сессии, чтобы после перезапуска приложения торренты восстанавливались и продолжали раздачу.[reference:10]
- **Удаление:** только по явной команде из админ-панели. При удалении торрент останавливается, файлы удаляются с диска (или перемещаются в корзину).

**Референсы:** `XayOn/torrentstream`, документация libtorrent по `add_torrent_params` (поля `save_path`, `seed_mode`), `resume data`, `set_piece_deadline`.

### Задача 4: Админ-панель (обязательный компонент)

**Цель:** Дать возможность управлять сохранёнными файлами и раздачей.

**Функциональность:**

- Список всех торрентов, которые были добавлены и сохранены на диск.
- Для каждого торрента отображать:
  - Название, качество, озвучка.
  - Статус (загрузка / раздача / пауза).
  - Прогресс загрузки.
  - Количество сидов/пиров, отданные байты, рейтинг (ratio).
  - Размер на диске.
- Кнопка **«Удалить»** для каждого торрента: останавливает раздачу и удаляет файлы с диска.
- Опционально: сортировка по размеру, дате добавления, рейтингу.

**Интеграция:**

- Если используется **TorrServer**: админ-панель обращается к его REST API (`/torrents`, `/torrents/{hash}`) для получения списка и удаления.[reference:11]
- Если используется **собственный прокси на libtorrent**: админ-панель обращается к API вашего Orchestrator, который управляет сессией libtorrent.

## 5. Критерии приёмки

1. **Поиск работает:** По запросу «Назад в будущее» возвращается непустой список раздач с полями «качество» и «озвучка» (или эти данные извлекаются из названия и отображаются пользователю).
2. **Стриминг работает:** Выбранная раздача начинает воспроизводиться до полной загрузки. Перемотка вперёд работает с разумной задержкой.
3. **Сохранение на диск работает:** Файлы скачиваются в указанную директорию на диске (`TorrentsSavePath`), а не только в оперативную память.
4. **Сидирование работает:** После завершения загрузки торрент **продолжает раздаваться**. В админ-панели виден статус «раздача», количество отданных байт и рейтинг.
5. **Файлы не удаляются автоматически:** После просмотра файлы остаются на диске. Удаление возможно **только вручную** через админ-панель.
6. **Админ-панель работает:** Можно просмотреть список сохранённых торрентов, их статус и удалить ненужные.
7. **Локальность:** Все компоненты работают на локальной машине или в домашней сети.
8. **Документация:** Есть README с инструкцией по запуску (Docker-команды, переменные окружения, зависимости, настройки `UseDisk` и `RemoveCacheOnDrop`).

## 3. TorrServer: диск, кэш, сидирование (по коду + частичный runtime)

### Подтверждение настроек в коде (MatriX.148)

- **`UseDisk`** — куски на диск в `{TorrentsSavePath}/{infohash}/`.
- **`RemoveCacheOnDrop`** — при `Close()` кэш удаляется **только если `true`** (`cache.go`).
- Дефолты в UI: `UseDisk: false`, `RemoveCacheOnDrop: false` (`defaultSettings.js`).

### Поведение, важное для вашего сценария

1. **`/settings` action `set` с частичным JSON** перезаписывает конфиг — в логе после set **`DefaultTrackers` обнулился**, был **`drop all torrents`**. Для orchestrator: **GET → merge → SET полный объект**.
2. **`cleanCache()` при старте** при `RemoveCacheOnDrop=false` удаляет каталоги-хеши **не** привязанные к торрентам в БД. Нужны **`save_to_db: true`** и персистентный список торрентов.
3. Статус в API — не классический qBittorrent «seeding», а `stat_string`: `Torrent working`, плюс **`bytes_written_data`**, **`connected_seeders`**, **`loaded_size` / `torrent_size`**.

### Runtime-тест (ограниченный)

- TorrServer **8090** запущен, **`UseDisk=true`**, **`TorrentsSavePath=/tmp/home-cinema-research/torrents`**, **`RemoveCacheOnDrop=false`** — применилось (лог `Client config`).

1. **Клиент TorrServer**

2. **Стрим**
   - После `add` и metadata — URL вида  
     `/stream/{filename}?link={hash}&index={file_id}&play`.
   - Опционально: открытие VLC/MPV через subprocess или вывод URL.
3. **Персистентность**
   - Данные TorrServer в volume (`--path`).
   - Orchestrator хранит «человеческие» метаданные (запрос, provider, title, quality, voice) в SQLite/JSON рядом с hash.

1. **REST**
   - `GET /search?q=...`

   - `DELETE /torrents/{hash}?delete_files=true` — drop + явное удаление файлов в `TorrentsSavePath` (на случай orphan при `RemoveCacheOnDrop=false`).
2. **CLI** — те же операции для отладки без UI.
